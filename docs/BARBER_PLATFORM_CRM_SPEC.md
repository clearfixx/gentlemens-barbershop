# Gentlemen’s Barbershop — Barber Platform & CRM Evolution

> **Technical specification / Product requirements**  
> Revision: 1.0 · Date: 2026-11-16 · Language: Ukrainian  
> Status: **planning / agreed direction**, not proof of implementation  
> Working integration branch: `feat/homepage-refinement`

## 1. Мета та статус рішень

Створити єдину систему, в якій публічний сайт мережі, персональні профілі барберів, бронювання, кабінет барбера, адміністрування та погодження змін працюють із тими самими даними. Пріоритет — реальна користь для клієнта й персоналу, а не побудова повноцінної ERP до запуску.

У документі:
- **Погоджено** — рішення, прямо схвалені в обговоренні: публічні професійні профілі, портфоліо, послуги, відгуки, соцпосилання, власний кабінет барбера, редагування його професійних даних із погодженням; соціальні feed-віджети відкласти.
- **Цільова вимога** — деталізація погодженого напряму, яку слід уточнити перед розробкою (URL, конкретні екрани, поля, API-контракти).
- **Пропозиція / майбутній етап** — заявки на відпустки, розширена CRM, аналітика, інтеграції, SaaS; це **не затверджений обсяг v1.0**.
- **Відкрите рішення** — потребує окремого затвердження чи синхронізації з паралельною роботою над адмінпанеллю.

## 2. Продуктові межі

### 2.1 Модулі

| Модуль | Призначення | Пріоритет |
| --- | --- | --- |
| Public Barber Profile | Публічна персональна сторінка кожного майстра | P0, перший пакет |
| Barber Profile Content | Біографія, спеціалізація, портфоліо, курси, сертифікати, соцмережі | P0/P1 поступово |
| Barber Dashboard | Перегляд власних записів; підготовка пропозицій щодо оновлення профілю | P1, після публічного профілю |
| Content Approval | Чернетки, модерація, ухвалення/відхилення, аудит публікації | P1, залежить від адмінки |
| Booking Integration | Персональні послуги, вільні слоти й запис із профілю | P0/P1, поетапно |
| Staff Management | Графіки, винятки, вихідні, запити на відпустку | Пізніший етап |
| Customer CRM / Analytics | Історія візитів, відгуки, лояльність, аналітика мережі | Поступове розширення |
| External Social Feeds | Instagram та інші вбудовані сторонні віджети | Після v1.0 |

**Non-goals початкового пакета:** зарплати, POS, складський облік у межах цього ТЗ, повна ERP, комерційна SaaS-мультиорендність, автоматичне зчитування Instagram.

### 2.2 Принципи

1. Один авторитетний профіль барбера, а не окремі незв’язані дані для сайту й кабінету.
2. Публічна сторінка читає лише опубліковані дані.
3. Барбер редагує **пропозицію**, а не опублікований запис напряму.
4. Доступ і схвалення перевіряються на сервері; прихований пункт меню не є захистом.
5. Ціна, тривалість, графік, доступність і статус запису визначаються на сервері.
6. Функціонал вводиться незалежними пакетами; стабільний `main` не має страждати від паралельної розробки.
7. UA/EN для всіх публічних текстів; доступність і SEO — частина приймання.

## 3. Публічний профіль майстра

### 3.1 Маршрут та SEO

**Пропонований маршрут:** `/[locale]/barbers/[slug]`, приклад `/uk/barbers/alex-morgan`.

- `slug` стабільний, унікальний, URL-safe; бажано не прив’язувати до редагованого ПІБ.
- Перевірка `locale`; `404` для прихованих/відсутніх майстрів.
- Мовно-залежні title, description, canonical, hreflang, Open Graph.
- Зміна slug: рішення щодо 301-переадресацій до реалізації.
- Не публікувати приватні контакти, внутрішні коментарі, чернетки, невалідувані досягнення.

### 3.2 Секції профілю

1. **Hero-профіль:** портрет, ПІБ/публічне ім’я, спеціалізація, заклад(и), біографія, CTA «Записатися».
2. **Про майстра:** досвід, напрямки, техніки, професійна історія, навички; жодних вигаданих регалій.
3. **Портфоліо:** фотографії робіт із підписом, альтернативним текстом, сортуванням та галереєю; лише погоджені медіа.
4. **Послуги:** доступні конкретному барберу позиції, персональна вартість і тривалість із серверного джерела; не вигадувати «від» без коректного визначення мінімуму.
5. **Графік / доступність:** реальні вільні дати й слоти за обраним закладом та послугою; за відсутності даних — стан «час уточнюється», без фейкових слотів.
6. **Відгуки:** лише опубліковані відгуки, прив’язані до барбера; рейтинг обчислюється з допустимих записів; коректний empty state.
7. **Соціальні мережі:** компактні кнопки зовнішніх посилань (Instagram, Facebook, Telegram, сайт тощо), тільки для заповнених валідних URL.

**Цільовий UX:** велика фотографія, преміальна типографіка Inter, крем/шоколад, матове золото, flat design, дві теми, мобільна адаптація, CTA для запису в помітному місці. Не копіювати чужі фотографії без дозволів.

### 3.3 Соцпосилання

Пропонована структура `socialLinks[] = { platform, url, label?, sortOrder? }`. Дозволені лише безпечні `https:` URL, за погодженої політики можливі окремі `mailto:`/інші протоколи, але **ніколи** `javascript:`. Для зовнішніх вкладок: `target="_blank"` разом із `rel="noopener noreferrer"`. Без автозапуску сторонніх віджетів.

Instagram Feed Widget та кастомні віджети — **backlog після v1.0**: окремий провайдерний адаптер, згода й авторизація акаунта, токени, кеш, квоти API, fallback і політика приватності.

## 4. Barber Dashboard

### 4.1 Призначення

Барбер самостійно підтримує актуальність власного професійного представництва: біографія, фотографії робіт, сертифікати після курсів, кваліфікація та соціальні посилання. Власник мережі не повинен вручну збирати все для кожного співробітника.

### 4.2 Екрани

- **Огляд:** найближчі записи, стан надісланих змін, швидкі дії.
- **Мій профіль:** редагування чернетки публічних даних, попередній перегляд до відправлення.
- **Портфоліо:** додати/видалити/переставити роботи в чернетці, медіа й підписи.
- **Курси та кваліфікація:** навчання, сертифікати, дати, опис; статус перевірки.
- **Соціальні мережі:** додати або змінити власні посилання.
- **Мої записи / графік:** операційна зона, що використовує вже наявний booking domain. Не розробляти другу систему графіків.
- **Мої погодження:** історія версій, стани, причини повернення та повторна подача.

**Додаткові заплановані можливості:** заявки на вихідні/відпустку, особиста статистика, сповіщення. Не є обов’язковою умовою запуску публічних профілів.

### 4.3 Межа редагування

| Барбер пропонує на погодження | Керує адміністрація |
| --- | --- |
| Біографія, професійний опис, спеціалізація | Роль і права доступу |
| Портрет/портфоліо та підписи | Прив’язка до закладу та статус працівника |
| Курси, сертифікати, досягнення | Офіційні персональні ціни й тривалості |
| Посилання на соцмережі | Політика записів і робочого графіка |

У майбутньому операційні заявки (вихідний, відпустка) мають **окремий workflow**, а не використовують ревізії публічного контенту.

## 5. Approval Workflow

### 5.1 Контентні зміни

Цільові стани: `draft → pending → approved | rejected` (у разі відхилення повернення до нової чернетки й повторна подача). За потреби додати технічні стани `published` / `superseded` для аудиту; не плутати «схвалено» з «опубліковано».

1. Барбер редагує свою чернетку або готує набір пов’язаних змін.
2. Сервер створює незмінний snapshot пропозиції із `baseRevision`.
3. Барбер надсилає пропозицію; публічний профіль залишається на попередній версії.
4. Адміністратор бачить diff, медіа, автора, дату й причину.
5. Схвалення виконує атомарне застосування зміни до опублікованої версії, після перевірки конфліктів та прав.
6. Відхилення/повернення вимагає коментаря; барбер бачить причину та може переробити чернетку.
7. Всі переходи журналюються: актор, час, зміни, результат, версія.

**Відкрите рішення:** чи достатньо одного погодження адміністратором закладу, чи обов’язкове фінальне схвалення мережею. Обговорений базовий напрям — контрольована автономія з остаточним контролем мережі; майбутнє делегування залежить від політик. Ніякої самопублікації без спеціально затвердженого дозволу.

### 5.2 Захист від конфліктів

- Барбер змінює **лише власний** профіль, перевірений за зв’язком Payload user ↔ barber; не довіряти `barberId` із клієнта.
- Optimistic locking через `baseRevision`; stale proposals не перезаписують новіші дані.
- Редагування статусу пропозиції, автора й ролей заборонене клієнту.
- Медіа перевіряються на формат, розмір, право використання, приватність та помірність контенту.
- Схвалення і публікація — серверні операції, повторне виконання має бути безпечним.
- Повідомлення про результат допускається після успішного коміту; помилка повідомлення не скасовує публікацію.

## 6. Ролі та права доступу

**Поточний стан у перевіреній гілці:** `Users.role` у Payload допускає `customer`, `barber`, `admin`. Доступ до Payload admin зараз лише для `admin`; окрема роль адміністратора закладу поки не визначена у цій схемі.

**Цільова модель (синхронізувати з адмінпанеллю):**
- Customer: публічні профілі, власні записи й відгуки.
- Barber: власні операційні дані та пропозиції публічного контенту.
- Location administrator: операції лише своїх закладів і, якщо дозволено політикою, перший рівень погодження.
- Network administrator: централізоване керування, фінальне погодження за обраною політикою, аудит.

**Обов’язково:** server-side RBAC + scope на заклад/майстра, відсутність IDOR, захист Payload collection access та route handlers, аудит дій; ролі не змінюються через редагування власного профілю. Конкретні назви ролей і матриця прав беруться зі спільної затвердженої адмін-архітектури, а не вводяться паралельно окремим кодом.

## 7. Інтеграція з бронюванням

Публічний профіль повинен дозволяти розпочати Booking Wizard із вибраним майстром, а за потреби — послугою та закладом. **Це лише початковий вибір UI**. Сервер перевіряє активність майстра, заклад, набір послуг, ціну, тривалість, розклад, доступність та перетини слотів.

Обов’язкове використання наявного booking domain:
- часові значення в базі UTC; відображення за часовим поясом закладу;
- перерви, винятки, вихідні та підтверджені відсутності впливають на слот;
- кілька послуг — суцільний слот сумарної тривалості;
- бронювання — транзакційне, ідемпотентне, з DB-захистом від перетинів;
- поточна політика: `pending` резервує слот; право підтвердження, скасування й дедлайни — серверні.

**Не вигадувати query-параметри чи нові endpoint-и**, доки не звірено контракт поточного Wizard. Deep-link/preselection — окреме завдання з інтеграційними тестами.

## 8. Staff Management: відсутності та відпустки (майбутній пакет)

Ідея розвитку: барбер подає заявку на відпустку, адміністратор погоджує, а система враховує відсутність у слотах.

Рекомендований окремий процес:
`draft → submitted → approved | rejected | cancelled` — **попередня пропозиція, не затверджений контракт**.

Потрібні правила до реалізації:
- діапазон дат і часовий пояс закладу, тип відсутності, коментар, статус, історія рішень;
- конфлікт із уже створеними активними бронюваннями: **не схвалювати мовчки**; запропонувати процедуру перенесення/скасування з повідомленнями;
- атомарне застосування до графіка/винятків після погодження;
- повторні запити, дублювання, перетини між відсутностями;
- scope адміністратора по закладах, делегування відповідальності;
- політики трудового й кадрового обліку — окремо, не в цьому ТЗ.

Безпосередні блокування часу вже належать booking/schedule domain; заявка на відпустку не повинна створювати окрему конкуренцію за слоти.

## 9. CRM, аналітика та SaaS (roadmap, не v1.0)

**CRM:** клієнтська історія, повторні відвідування, відгуки, лояльність, комунікації. Мінімізувати доступ барберів до персональних даних клієнтів: лише те, що потрібно для їхніх записів.

**Аналітика:** завантаження майстрів, популярність послуг, кількість візитів, конверсії профіль → запис. Метрики мають визначення, часовий пояс, правила обліку скасувань та відсутніх даних; не показувати вигадані KPI.

**Пізніше:** складський облік, нарахування зарплат, фінанси/POS, зовнішні календарі, Instagram widgets, ширша ERP та, лише після окремого бізнес-рішення, SaaS. Модульність зараз — не вимога будувати multitenancy завчасно.

## 11. Технічна реалізація

- **Стек:** існуючий Next.js App Router + TypeScript + Payload CMS + PostgreSQL. Не вводити NestJS/Supabase/мікросервіси.
- Публічні сторінки: server components та обмежені `overrideAccess:false` публічні запити, лише опубліковані дані.
- Dashboard: protected routes, окремі server actions/handlers, валідація Zod/еквівалент, server checks.
- Файли через налаштований медіа-шар Payload; ліцензії, обмеження розміру, alt, безпечний upload.
- Сторінки оптимізувати під mobile-first, UX клавіатури й reduced-motion.
- Не відкривати внутрішні чернетки для SEO, sitemap чи кешу.
- Модерація не повинна випадково інвалідувати бронювання чи змінювати ціни.
- Перед schema changes: review міграцій і rollback план; тести в ізольованій БД.

## 13. Критерії приймання

**Профіль:** коректний slug/404, усі дані із CMS, без прихованих чернеток, валідні соцпосилання, робоча двомовність, адаптивність, доступність з клавіатури, нормальний SEO. Не відображати вигадані рейтинги, слоти чи ціни.

**Погодження:** барбер не може публікувати напряму; не може редагувати іншого барбера; адміністратор не бачить/не схвалює чужий заклад без відповідного scope; повторні дії та stale revisions відхиляються або обробляються безпечно; аудит повний.

**Бронювання:** preselection проходить перевірку, сервіс визначає ціну й доступність, паралельні запити не створюють перетини, статуси й відсутності враховані.

**Quality gates:** `pnpm lint`, `pnpm typecheck`, `pnpm build`, unit/integration tests для permissions, revision transitions, booking preselection; ручний QA light/dark, desktop/tablet/mobile та reduced-motion. Всі необхідні міграції і regression checks пройдено перед merge.

## 14. Відкриті питання

1. Остаточна матриця `network_admin / location_admin` та назви ролей — узгодити з паралельною адмін-розробкою.
2. Хто має право фінальної публікації, які види змін може затверджувати адміністратор закладу?
3. Чи дозволено редагувати опублікований slug і як підтримувати редиректи?
4. Чи мають сертифікати документально підтверджуватись до публікації?
5. Політика медіа: розмір, авторські права, згоди клієнтів на фото робіт, видалення.
6. Де проходить межа між графіком барбера, відсутністю, відпусткою і службовою заявкою?
7. Формат deep-link передачі preselected barber/service/location у Wizard — погодити контракт.
8. Чи потрібен окремий «сховати профіль майстра» і що відбувається з існуючими бронюваннями?
